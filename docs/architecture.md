# ARES architecture

Status: proposal for Core 0.1; not an implementation claim.

## Scope

Core 0.1 proves authenticated two-peer communication over a viable IP network, including a local-network mode that does not depend on internet access. It independently detects and diagnoses failure in each direction.

It does not yet prove global NAT traversal, browser parity, production multiparty scale, or a 100x reliability improvement.

## Logical components

1. Application API: session creation, peer identity, permissions, streams, lifecycle.
2. Session/control: authenticated setup, capability exchange, stream intent, idempotent transitions, teardown.
3. Identity and key management: peer authentication, key agreement, transcript binding, rotation, revocation.
4. Transport adapter: selected reliable and datagram-capable transports, framing, congestion and flow control.
5. Connectivity manager: local discovery, interface selection, address validation, path health, later NAT traversal and relay policy.
6. Data plane: reliable ordered streams and deadline-bound messages with explicit expiry.
7. Reliability supervisor: independent directional probes, timers, bounded retries, path switching, subsystem recovery.
8. Diagnostics: privacy-safe counters, events, histograms and state transitions.

Interfaces must be explicit and versioned. Media capture, codecs, rendering and device routing are deferred until the media milestone.

## Non-negotiable invariants

### I1 — Directional health is independent

For peers A and B, track A_TO_B and B_TO_A separately. A session is bidirectionally healthy only when both required directions satisfy the health policy. A transport handshake or socket state is not proof of application delivery.

### I2 — Health evidence traverses the measured path

A directional probe is generated by the sender, authenticated by the receiver, and acknowledged using explicitly defined semantics. Record probe generation, transport acceptance, remote receipt, authentication result, application delivery, and acknowledgement receipt separately. A local send success is not end-to-end health.

### I3 — Control and data failure are separable

Failure of an optional data stream must not automatically destroy a healthy control channel. Internet loss must not terminate a session whose local path remains valid.

### I4 — Recovery is bounded

Every retry, queue, buffer, parser allocation, handshake, and timer has a documented limit. Recovery has a deadline and terminal failure reason.

### I5 — Security precedes trust

Discovery results are hints, not authenticated identities. No peer data is trusted before cryptographic authentication. No silent plaintext or weaker-suite fallback.

### I6 — Delivery semantics are explicit

Each stream declares reliable/ordered or time-sensitive/deadline-bound behavior. Expired time-sensitive data is dropped rather than silently delivered late.

## Directional state model

Each direction has its own state: UNKNOWN, STARTING, HEALTHY, DEGRADED, FAILED, RECOVERING. Every transition records timestamp, reason code and evidence. Hysteresis may prevent flapping but must not hide failure beyond the detection budget.

The aggregate session state is derived:
- BIDIRECTIONAL_HEALTHY: both required directions healthy.
- DEGRADED: at least one direction degraded while another remains usable.
- ONE_WAY: one direction failed and the opposite direction is healthy.
- UNAVAILABLE: neither direction meets policy.
- CLOSING or CLOSED: lifecycle states.

Aggregate state never overwrites directional evidence.

## Candidate transport strategy

Evaluate mature options before inventing a transport:
- QUIC streams for reliable ordered control/data.
- QUIC DATAGRAM or another bounded datagram path for deadline-bound data.
- WebTransport for browser environments where supported.
- Native UDP only where platform access and security design justify it.

QUIC alone does not provide local discovery, NAT traversal, codecs/capture, group key management, or browser raw-socket access. Transport choice requires an ADR covering platform support, LAN behavior, congestion, loss, MTU, migration, security and complexity.

## Local-first connection flow

1. Discover or manually enter a peer endpoint on the local network.
2. Treat the endpoint as untrusted; authenticate using an out-of-band pairing secret, verified fingerprint, or another specified trust bootstrap.
3. Negotiate protocol version and capabilities with downgrade protection.
4. Establish encrypted transport and bind authenticated identity to the handshake transcript.
5. Run independent A_TO_B and B_TO_A application-level probes.
6. Declare usability only according to requested directionality and stream policy.
7. Continue health probes and privacy-safe telemetry.
8. Validate an alternate path before switching; do not discard a working path prematurely.

Multicast, broadcast, mDNS, QR and manual pairing are candidates, not assumptions. Wi-Fi client isolation, VLANs, host firewalls, multicast filtering and OS permissions can prevent same-LAN reachability.

## Browser boundary

Ordinary web pages do not have general-purpose raw UDP socket access. A browser runtime must use supported APIs such as WebTransport where available, a local companion/gateway, or another justified standards-based approach. Native/browser parity must be tested, not promised.

## Reliability measurements

Let S_AB and S_BA denote successful end-to-end delivery in each direction over a defined interval.

- Bidirectional success: P(S_AB AND S_BA); measure jointly rather than assuming independence.
- One-way failure: P(S_AB XOR S_BA).
- Failure improvement: baseline_failure_rate / ARES_failure_rate, for identical metric definitions and conditions.
- Report absolute rates, median, p95, p99, confidence intervals, sample sizes and topology/device strata.

A 100x ratio is not meaningful if the baseline has zero observed failures or test conditions differ.

## ADR policy

Decisions about language, transport, crypto suite, wire format, discovery or browser gateway require an ADR with context, constraints, options, evidence, security/performance implications, decision and reversal conditions.
