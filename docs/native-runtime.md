# Native two-peer runtime

## Scope

The native runtime is an authenticated heartbeat and directional-health proof of
concept. It is not yet a general-purpose media or data transport.

Each process:
- opens an outbound TCP/TLS connection to its peer and listens for the peer's
  independent outbound connection;
- requires a CA-validated client certificate and checks the peer leaf
  certificate against a SHA-256 pin on both accepted and outbound connections;
- sends monotonically sequenced application heartbeats;
- records locally submitted heartbeats as pending, never as delivered;
- observes inbound heartbeats at the receiver and emits received/missing
  reports over its own outbound connection;
- applies authenticated peer reports to its outbound direction ledger;
- maintains independent A→B and B→A evidence.

The two independent TCP connections are important: a packet blackhole on A→B
must not also suppress B→A application traffic through TCP's bidirectional
acknowledgement dependency on a single connection.

## Build

    cargo build --bin ares-peer

The runtime expects DER-encoded CA, leaf certificate, and PKCS#8 private key
files. The leaf certificate must contain the peer's DNS name (a or b) as a
SAN and permit both clientAuth and serverAuth. Both peers must trust the same
CA and pin the other peer's exact leaf SHA-256 fingerprint.

Example invocation shape:

    ares-peer a 192.0.2.10:41001 192.0.2.11:41001 b ca.der a.der a-key.der <b-cert-sha256> <32-hex-session-id>
    ares-peer b 192.0.2.11:41001 192.0.2.10:41001 a ca.der b.der b-key.der <a-cert-sha256> <same-session-id>

Use unique, securely provisioned peer certificates and session identifiers in
real deployments. The test CA generated by the fault-injection script is only
for an ephemeral CI test.

## Directional evidence semantics

- A locally accepted TCP write is pending evidence, not delivery.
- An inbound heartbeat directly observed by this endpoint proves that inbound
  direction was working at the observation time.
- A missing heartbeat is emitted by the receiver only after the negotiated
  observation deadline. The report is sent on the receiver's independent
  outbound TLS connection.
- A one-way classification requires one direction to be receiver-confirmed
  healthy and the other to have crossed the configured explicit missing-report
  failure threshold.
- A missing heartbeat means the scheduled application heartbeat was not
  observed before its deadline. It does not identify whether the cause was
  packet loss, congestion, a paused process, or a failed path.

This runtime is TCP/TLS only. It does not yet provide QUIC DATAGRAMs, media,
NAT traversal, discovery, relay selection, browser support, or offline-LAN
certification. The CA is a trust anchor; certificate pinning narrows that trust
to the configured peer identity. Revocation, automated key rotation, durable
identity storage, and production pairing are not implemented.

## Real packet-drop test

On Linux with root privileges, iproute2, OpenSSL, and a built binary:

    cargo build --bin ares-peer
    sudo bash scripts/test-directional-packet-drop.sh

The script creates two network namespaces connected by a veth pair, starts two
independent peer processes with mutually authenticated TLS, waits for a
bidirectionally healthy baseline, then applies tc netem loss 100% to A's
egress interface only. It passes only if endpoint A reports:

    session=OneWay a_to_b=Failed b_to_a=Healthy

The CI job runs this same test. A passing unit test or an application-level
drop simulation is not a substitute for this network-layer experiment.
